## 한눈에 보기

| | |
|---|---|
| **하는 일** | 표마다 제각각인 KOSIS 원본을 **같은 규칙으로 정리**해서, 이후 단계가 원본 표기 차이를 신경 쓰지 않게 한다 |
| **입력** | `kosis_data/catalog.csv`, `kosis_data/raw/<조사>/<기관_표>.csv`, `kosis_data/meta/<기관_표>.json` (읽기만) |

| **규칙 출처** | `ys_work/view_model.ipynb` 2단계(0~9장). **규칙은 한 글자도 바꾸지 않고** 옮김 |

메타 JSON ─┘        (4-3, 4-4)          (5장)                                  (5장)

규칙 상수 ───────────────────────────────────────────────────▶ dict/*.json (7장)

## 1. 왜 필요한가

View 는 "표를 어떤 조건으로 잘라 보여줄까"인데, 그 조건(지역·시점·합계)이 표마다 다르게 적혀 있으면 일관되게 자를 수 없다.

| 원본의 문제 | 예 | 정규화 후 |
|---|---|---|
| 시점 표기가 제각각 | 원본 `A`, 메타 `년`/`5년` | `prd_se = Y`, `year = 2024` |
| 숫자 칸에 부호 | `1,234`, `X`, `-` | `value = 1234.0` / `NULL` + `symbol = X` |
| 지역 표기가 제각각 | `강원도` / `강원특별자치도`, 코드 `11` / `1110100A11` | `c1_std = 강원특별자치도`, `geo_type = 시도` |
| 합계가 무엇인지 표마다 다름 | `총인구`와 `합계`가 한 분류에 같이 있음 | `c2_total = true` 는 `합계` 하나만 |

## 2. 코드 구성 (위에서 아래 순서)

### 2-1. 시점 규칙 (`PRD_SE_MAP`, `se_case_sql`, `PERIOD_*_SQL`)
- 원본/메타의 시점 구분을 표준 코드로: `A·Y·년·연 → Y`, `Q·분기 → Q`, `IR → IR`, `N년 → F`(다년주기)
- `PRD_DE`에서 숫자만 뽑아 앞 4자리 = 연도, 다음 2자리 = 월·분기 번호
- 결과 컬럼 3개를 목적별로 나눔
  - `year` (정수): "2024년 ~" 필터용
  - `period_label`: 사람이 읽는 표기 (`2024 1분기`)
  - `period_date`: 정렬용 날짜

### 2-2. 값과 부호 (`DEFAULT_SYMBOL_MEANING`, `symbol_meanings`)
- 숫자로 바뀌면 `value`, 안 바뀌면 `value = NULL` + `symbol` 에 원래 부호 보관. **0 으로 바꾸지 않음** (틀린 답이 되므로)
- 부호 의미는 **표 주석(CMMT)에 설명이 있으면 그 문장**, 없으면 KOSIS 일반 의미 (`X` = 비밀보호)

### 2-3. 분류 판정 (`level_kind`, `pick_totals`, `std_geo_name`, `geo_type_of` …)
분류(C1~C8)마다 "무슨 종류인가"를 쿼리 모듈의 조건 이름으로 판정한다.

| kind | 판정 근거 (분류 이름) | 붙는 속성 |
|---|---|---|
| `nationality` | 국적·내외국인 (국적**취득**은 제외) | — |
| `regions` | 행정구역·시도·시군구·지역 | `std`(표준명), `geo_type`(전국/시도/시군구/읍면동/동읍면부) |
| `scenario` | 시나리오·가정별 + 코드에 '추계' | `std`(중위/고위/저위), `is_default`(중위) |
| `cohort` | 년생·코호트 | `cohort_from/to` |
| `sex` | 성별, 또는 코드가 전부 남/여 | — |
| `ages` | 연령·세별, 또는 코드 60% 이상이 `N~M세` | `age_from/to` (숫자 범위) |
| `other` | 위에 해당 없음 | 이름으로 매칭 |

- **판정 순서가 중요**: `국적(지역)별` 은 '지역'이 들어 있지만 국적이므로 국적을 먼저 본다.
- **합계 판별 (`pick_totals`)**: 강한 합계(`합계·계·전국·전체…`)가 있으면 그것만 → 없으면 약한 합계(`총인구·총수`) → 없으면 `0`으로만 된 코드.
  이 규칙이 "서울 외국인 수"에 서울 전체 인구(9,335,444)가 아니라 외국인 합계(450,888)를 꺼내게 한다.
- **지역 표준명 (`SIDO`, `std_geo_name`)**: 시도 17개의 현재 공식 명칭을 표준으로, 옛 이름·줄임말은 별칭. `광주시`는 경기도 광주시와 겹쳐 별칭에서 뺌.
- **동부/읍부/면부**: `geo_type = 동읍면부` 로 따로 표시. 시도와 함께 더하면 전국이 2배 이상 잡히므로.
- **기본값 (`default_code`)**: 조건이 없을 때 쓸 코드. 합계 → 없으면 중위 추계 → 없으면 첫 코드 (이유는 `default_reason` 에 기록).

### 2-4. 메타 → 코드 사전 (`parse_meta`, `match_levels`, `build_level_dims`, `build_item_dims`)
1. 메타 `ITM` 을 분류 목록과 항목 목록으로 나눔
2. 원본 컬럼 `C1, C2…` 와 메타 분류를 **이름(`C{i}_OBJ_NM`)으로** 짝지음. 실패하면 순서로. (순서만 믿으면 지역 코드에 성별 이름이 붙는 조용한 오류가 생김)
3. 상위코드가 없으면 추정: 지역은 코드 접두어(`11` ⊃ `11320`), 연령은 숫자 범위 포함(`80세이상` ⊃ `80~84세`)
4. 코드마다 `label / std / ord(정의 순서) / depth(계층) / is_total / geo_type` 을 붙임
5. 항목(ITEM)도 같은 방식: 연령이 항목으로 들어온 표는 `itm_kind = ages`

### 2-5. 표 하나 정규화 (`normalize_table`)
- DuckDB SQL 한 번으로 **원본 CSV 읽기 → 코드 사전 조인 → 시점·값·단위 정리 → 정렬 → parquet 저장**. 큰 표(740MB)도 메모리에 다 올리지 않음
- 단위: 원본 → (비었으면) 같은 항목의 최빈 단위 → 메타 단위. 채운 경우 `unit_inferred = true`
- **증분 처리**: parquet 이 원본보다 새로우면 다시 만들지 않고 기존 프로필을 읽음

### 2-5-1. 지연 정규화 (`ensure_normalized`)
- 표를 미리 정하지 않기 위한 입구. `resolve.py` 가 992개 중 표를 고르면 `ensure_normalized(con, "DT_1B040A3")` 를 부른다
- 내부에서 카탈로그 행을 찾아 `normalize_table` 을 호출 → **캐시(원본보다 새 parquet)가 있으면 프로필만 읽고**(0.03초), 없으면 그때 정규화
- 카탈로그(`selected == True`)에 없는 표면 `ValueError`

### 2-6. 프로필 (`build_profile`)
- 메타가 아니라 **방금 만든 parquet 을 다시 집계**한다. 메타에만 있고 실제 데이터에 없는 코드를 빼기 위함
- `row_check`: 원본 행 수 vs 정제 행 수. `dropped` 가 0 이 아니면 시점을 못 읽어 행이 사라진 것

### 2-7. 검증 (`check_total`)
- 최신 시점, 다른 분류는 합계로 고정하고 **합계 코드 값 vs 바로 아래(depth 1) 코드 값의 합**을 비교
- 비율 ≈ 1.0 이면 합계 판별과 계층이 맞음

### 2-8. 사전 내보내기 (`export_dicts`)
쿼리·RAG 모듈과 표기를 맞추기 위한 파일 4개: `region_dict`(시도 표준명·별칭), `period_rules`(시점 코드), `symbol_dict`(부호 의미), `dim_kinds`(분류 종류 판정 규칙)

## 3. 출력 형식

### `processed/<기관_표>.parquet` — 한 행 = 원본 셀 하나

| 컬럼 | 설명 | 예 |
|---|---|---|
| `table_key`, `org_id`, `tbl_id` | 표 식별자 | `101_DT_1B040A3` |
| `prd_se`, `prd_de`, `year`, `period_label`, `period_date` | 시점 | `Y`, `2024`, 2024, `2024`, 2024-01-01 |
| `c{i}_code`, `c{i}_name`, `c{i}_label`, `c{i}_std` | 분류 i 의 코드·원래 이름·구분 이름·표준명 | `22`, `대구광역시` … |
| `c{i}_ord`, `c{i}_depth`, `c{i}_total`, `c{i}_geo_type`, `c{i}_parent` | 정의 순서·계층·합계 여부·지역 유형·상위 코드 | |
| `itm_id`, `itm_nm`, `itm_ord`, `itm_kind`, `itm_total` | 항목 | `T20`, `총인구수` |
| `unit`, `unit_inferred` | 단위, 추정으로 채웠는지 | `명`, false |
| `value`, `value_raw`, `symbol` | 숫자 / 원래 문자열 / 부호 | 2,374,960 / `2374960` / NULL |

### `profiles/<기관_표>.json` — 표 구조 요약 (③ resolve 가 표를 고를 때 쓰는 핵심 자료)

| 키 | 내용 |
|---|---|
| `tbl_nm`, `survey_nm`, `dept_nm`, `path` | 표 이름·조사명·작성 부서·메뉴 경로 |
| `periods`, `latest`, `cycles` | 실제 있는 시점 목록, 최신 시점, 메타상 주기 |
| `levels[]` | 분류마다 `kind`, `obj_nm`, `total_code`, `default_code`, `geo_types`, `codes[]` |
| `items[]` | 항목마다 `itm_id`, `name`, `unit`, `kind`, `is_total` |
| `symbols`, `notes`, `row_check` | 부호 개수·의미, 표 주석, 행 보존 확인 |

## 5. 알려진 문제 (규칙은 고치지 않고 다음 단계에서 처리)

| # | 문제 | 영향 | 처리할 곳 |
|---|---|---|---|
| ① | 세종·울산 하위 코드(`세종시`, 옛 `울산시`)가 시도로 중복 판정 | 시도별 비교에서 두 줄 | ③ resolve / ④ build_view 에서 시도 비교 시 중복 표준명 제거 |
| ② | 단위 없는 표 3개 (`DT_1BPB003`, `INH_1B8000F_02`, `DT_1BPA201`) — 원본에 `UNIT_NM` 컬럼 자체가 없음 | 비율/명 구분 불가 | View 메타에 "단위 미상" 표시, 항목명에 단위가 있으면(`(천명)`, `(%)`) 거기서 추출 검토 |
| ③ | 성별이 **항목**에 있음 (`DT_1B04005N`·`DT_1B040A3`: 총인구수/남자인구수/여자인구수) | 쿼리 `[성별] 남자`가 분류로는 안 맞음 | ③ resolve 에서 항목명으로 성별 매칭 |
| ④ | 지표가 **분류 코드 이름**에 있음 (`DT_1B8000G` 종류별: `출생아수(명)`, `INH_1B8000F_02`: `기대수명(출생시 기대여명) - 남`) | 기본값이 첫 코드라 의미 없음 | ③ resolve 에서 `[지표]`를 분류 코드 이름과도 매칭 |
| ⑤ | `DT_1B8000G` 메타 주기는 월·분기·연간이지만 정제 결과는 분기·연간만 | 월간 질의 불가 | 수집 단계 이슈 (`ys_work/NOTES.md`) |
| ⑥ | `DT_1BPB003` 인구종류가 `ages` 로 판정됐지만 실제로는 `생산연령인구(천명): 계` 같은 지표+단위 이름 | 연령 범위 매칭 부정확 | **처리 (11-03)**: build_view 가 연령 숫자 없는 ages 분류를 지표 분류로 처리 (`build_view.md` 4-2) |
